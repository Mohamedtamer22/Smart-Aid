# Testing plan and current evidence

Run `backend/.\mvnw.cmd test` and `mobile/flutter analyze; flutter test` before merging. The current checks passed on 2026-10-06. Backend tests verify lifecycle terminal states (including EMS eligibility), volunteer mission transition ordering, non-diagnostic triage prioritization, dispatch eligibility/skill filtering, capability exclusion, missing congestion explanation, score sensitivity, and account-scoped authentication throttling. Mobile tests verify Arabic/English emergency-action localization plus the shared presentation components used by the user, volunteer, EMS, and Smart ER flows; static analysis covers the client.

Native integration smoke evidence on 2026-10-06: PostgreSQL 18 + PostGIS, Flyway migration validation, API health, seeded local-role authentication, incident history, volunteer eligibility, EMS dashboard, Smart ER comparison, and unauthenticated EMS denial all passed. `scripts/verify-demo.ps1` repeats this non-mutating check against the fictional local scenario. Flutter Web release and Android debug assembly both built successfully after the UX refresh; generated outputs are intentionally ignored. The Android artifact is produced by `scripts/build-android-debug.ps1`, which retains Flutter's required Gradle build while applying a Windows-safe temporary directory. The test used fictional local data only.

`scripts/test-end-to-end.ps1` is the stateful native test: it creates uniquely tagged fictional records, validates registration and refresh-token replay protection, profile/contact CRUD, server-confirmed SOS, notification state, volunteer eligibility and mission state, role denial, authenticated STOMP delivery, EMS assignment, Smart ER comparison, valid incident transitions through resolution, and logout. It does not require external services and does not use live emergency data. A passing run was completed on 2026-10-06. The script cleans up its unfinished scenario automatically; `scripts/cleanup-e2e.ps1` is available for tagged records from an earlier interrupted run.

Still required before a production release: controller/security tests against a disposable test database (including profile ownership and concurrent volunteer acceptance), negative STOMP-authorization integration tests, Flutter auth/SOS/profile/Smart-ER widget tests with mocked GPS/API, an accessibility/RTL review, and a human-operated end-to-end demo. At the latest verification, no Android virtual device or physical Android device was connected; Android debug packaging succeeded and must be installed on an emulator or device for the final hands-on mobile acceptance pass. These are release-hardening activities, not current demo blockers. No test result is represented as an actual emergency-service validation.
